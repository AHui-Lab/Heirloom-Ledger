# 剧情任务架构

> [!note] 定位
> 本文规定如何“写清楚和审清楚”任务。状态名与字段是 Draft Proposal；在对应 Game Core schema 获得确认前，不是实现规则。

## 1. 任务不是差事清单

本项目中的任务，是一个玩家能够理解、调查、选择并承担后果的结构化问题。它可以包含买卖，但不应退化成“带来三件瓷器”或“把关系刷到某档”。

标准任务句式：

> **有人**因为某个可理解的理由，希望玩家对**一件物或一件事**作出处理；玩家必须在不完整信息中通过**交谈、观察、记录与经营选择**形成判断，而这个判断会在以后留下**可追踪的回响**。

## 2. 内容层级与 ID

| 层级 | 建议 ID | 说明 |
|---|---|---|
| 长期主线 | `MAIN-*` | 贯穿多个篇章的玩家与爷爷线 |
| 篇章 | `CH##` | 回答一个阶段性重大问题 |
| 任务线 | `CH##-Q##` | 可独立追踪的疑问、委托或人物纠葛 |
| 事件节点 | `CH##-Q##-N##` | 一次具体来访、记录、电话、信件或回访 |
| 后果节点 | `CH##-Q##-E##` | 由既往交易/选择触发的回响 |

ID 一旦进入数据或存档，不因标题润色而改变。此规则需在 schema 设计时另行确认。

## 3. 五类任务线

### 3.1 主线调查

围绕篇章中心疑问组织证据与选择。它负责改变玩家对爷爷、店铺或自身责任的理解。

### 3.2 人物线

围绕一个人的目标、顾虑、承诺和立场推进。人物线不能只用关系阶段代替；必须记录具体共同经历。

### 3.3 器物线

围绕某件物的真伪、年代、来源、状态、物权或流转展开。器物既是证据，也是可能被交易、保留、归还或误判的对象。

### 3.4 经营委托

从玩家日常经营自然进入，可提供资金、库存、知识或人脉机会。轻量经营内容不必强行连接爷爷主线，但应服从当天经营主题与来客容量。

### 3.5 后果回访

既往交易、客观错误陈述、承诺或公开选择在后来被发现、传播或重新解释。它不是“系统秋后算账”，而是让世界记得物与人如何流动。

同一节点可以承担两种职责，例如剧情人物带货上门，同时形成判断挑战；不因此额外增加一个来客名额。

## 4. 玩家可见的三栏任务表达

沿用沉浸式原型已经采用的信息层级：

| 栏目 | 只允许写什么 | 禁止写什么 |
|---|---|---|
| 已知事实 | 已取得的记录、已观察线索、已发生选择与获授权结论 | 后台真相、未传播事实 |
| 我的疑问 | 玩家目前有理由提出的问题 | 伪装成问句的答案提示 |
| 可走访方向 | 已开放人物、记录、地点或等待条件 | 精确隐藏门槛、最优路线 |

任务标题应描述疑问或责任，不应泄露答案。例如“账上的‘周’是谁”优于“证明周伯安不是原主”。

## 5. 节点状态机（Draft Proposal）

```text
Dormant 未进入视野
→ Available 条件满足、可被发现
→ Active 玩家已经接触并留下疑问/承诺
├─ Deferred 玩家明确暂缓，保留后续入口
├─ Resolved 当前问题得到有效处理
├─ Closed 玩家明确拒绝或破坏了该路线
└─ Echo 已解决事项在后续产生回响
```

- “稍后”必须与“拒绝”分开；第一章现有规格已要求延期类选项不永久消失。
- `Resolved` 表示当前节点已处理，不代表相关人物、器物或后果永远结束。
- 任何不可逆关闭都需要明确行为和反馈，不能因玩家没在某天点击而暗中关闭。

## 6. 节点的最小信息模型

每个节点在进入制作前至少写清：

| 字段 | 设计问题 |
|---|---|
| `id / title / status` | 它是什么、目前是否确认？ |
| `story_function` | 它推进主线、人物、器物、经营还是后果？ |
| `objective_truth` | 后台客观事实是什么？ |
| `actor_knowledge` | 每个相关人物知道、相信和不知道什么？ |
| `entry_conditions` | 哪些旗标、关系记忆、物件或公开信息使其可触发？ |
| `presentation` | 通过来访、物件、电话、信件、传闻还是记录出现？ |
| `player_visible` | 触发时玩家能看到哪些信息？ |
| `evidence` | 玩家凭什么作判断？怎样取得？ |
| `choices` | 选择的意图与差异是什么？ |
| `core_resolution` | Game Core 检查、拒绝或变更哪些状态？ |
| `llm_scope` | LLM 可以表达什么，绝不能补什么？ |
| `defer / close` | 暂缓和关闭分别怎样发生？ |
| `immediate_feedback` | 玩家当下如何知道选择被理解？ |
| `echo` | 哪些后续节点可能记住它？ |

完整填写格式见 [[QUEST_TEMPLATE]]。

## 7. 分支设计原则

### 真分支

至少在以下一项上产生差异：可用证据、人物具体记忆、物权/交易结果、公开说明、后续传播或下一事件入口。只换一句台词而不改变任何理解或未来可能性的，不应包装成重大选择。

### 不设标准答案陷阱

- 查证充分可以提供更清晰的选择，但不能保证利润最大。
- 保护关系可以有机会成本，但不必必然贫穷。
- 追求成交可以是合理选择，但必须对授权与说明负责。
- “保留待查”是有效结果，不应总被写成胆怯或失败。

### 失败向前

误判、拒绝或关系受损可以改变路线，但应留下新的可理解状态：知识反馈、不同证人、延迟机会或后果回访。它不能凭空还原玩家错过的证据，也不能让故事彻底无事可做。

## 8. 与营业循环的接口

所有任务必须服从 [[GAME_RULES]] 和 [[EVENT_SYSTEM]]：

- 剧情/特殊客人默认占用上午或下午标准名额。
- 普通标准营业日为约 4～6 名来客；重要例外必须由数据显式声明。
- 重要剧情不要求每天发生；纯经营日使用经营主题。
- 判断挑战需要预先存在有效线索与差异结果，不能由 LLM 临时制造反转。
- 玩家查阅账本、人物资料和鉴定记录不消耗时段或 NPC 耐心。
- 店外、夜间交流与拍卖目前在正式 V1 与原型范围之间仍有边界差异，编写新任务前需核对 [[DECISIONS]]。

## 9. Game Core / LLM 分工

```text
设计文档定义客观事实与允许的分支
→ Game Core 检查触发、物权、关系、记忆、旗标与结算
→ LLM 根据授权的角色认知和语气生成表达
→ Parser / Validator 验证意图
→ Game Core 执行状态变化
```

LLM 可以让周伯安把“手续不齐”说得像一个活人；它不能因为这句话很有戏，就决定存根已经找到。

## 10. 任务审阅门

任务进入实现前必须全部通过：

- [ ] 与 locked/confirmed 规则无冲突。
- [ ] 客观事实、角色认知、玩家已知和公共认知分离。
- [ ] 至少有一项玩家可获得的判断依据。
- [ ] 选择不是读心或无证据猜测。
- [ ] 暂缓、拒绝、失败和恢复路径已说明。
- [ ] 每项状态变化都指定由 Game Core 结算。
- [ ] LLM 边界明确，不允许补写真相。
- [ ] 当下反馈与跨日/跨章回响均有定义。
- [ ] 不把人物线简化成关系数值门槛。
- [ ] 有明确 Acceptance Criteria、测试思路与已知偏差。
